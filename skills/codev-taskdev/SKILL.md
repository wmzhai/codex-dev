# TaskDev

`codev-taskdev` 是 task plan 的手动执行器。它把已经审核通过的 task 文件转成实际代码改动，并把实现过程同步回任务文档。

它覆盖当前分支内的“选择任务 -> 校准 plan -> 编码 -> 持续同步 task -> 实现收尾精简 -> 迁移 / 编译 / 当前环境能做的端到端验证”。它不负责完整 QA 矩阵、分支部署、归档或主干收尾。停下来交给用户之前，必须先把本地能做的验证做完；不能只交代码、编译结果或任务文档，然后完全等用户去发现功能不可用。

## 第一规则：先用中文交流

- skill 一触发，第一句就用中文和用户交流。
- 整个执行过程中的进度更新、阻塞说明、实现摘要和结果汇报默认都用中文。
- 只有用户明确要求英文或双语时，才切换语言。

## 调用前缀

面向用户写出下一步 skill 入口时，必须使用当前宿主的调用前缀，不要把另一套宿主的前缀写进用户提示：

- Codex：`$<skill-name>`，例如 `$codev-quickship`
- Grok / Grok Build TUI：`/<skill-name>`，例如 `/codev-quickship`
- Claude Code：`/<skill-name>`，例如 `/codev-quickship`

判断依据：

- 当前会话身份是 Grok 或 Claude Code，或用户是用 `/skill` 触发的，用 `/`
- 当前会话身份是 Codex，或用户是用 `$skill` 触发的，用 `$`

## Inputs

从用户请求推断目标任务：

- 如果用户指定了任务编号或文件名，如 `T08` 或 `T08-foo.md`，使用该任务。
- 否则使用 `tasks/` 下任务号最小的待办任务文件，只识别文件名匹配 `^T\\d+-.*\\.md$` 的任务文件，并忽略 `tasks/done/` 与其他非任务文件。

## End State

完成时应尽量达到以下状态：

- 目标 task 已在当前分支上完成当前 plan 范围内的代码实现。
- 对应 `tasks/Txx-*.md` 已同步实际采用的实现路径、重要代码改动、已执行验证、仍需人工验收的项和剩余缺口。
- 已在收尾阶段自动执行过一次 `codev-simplify` 式语义不变精简；如果没有安全可做的精简，也已明确记录。
- 已按当前仓库约定完成必要的数据库迁移、默认 build / 最小编译校验，以及当前环境能做的基本端到端验证。
- 本地能迁的库已经迁过，本地能编译的已经编过，本地能登录、能点通、能打已配置外部接口的路径已经自己跑过；跑不通且无法修好的能力不得继续留在页面或后台。
- 只有当前环境确实做不到的验收才留给用户。用户确认那些项之后，再进入当前宿主对应的 `codev-quickship` 入口。

`codev-taskdev` 默认不负责以下动作：

- 不自动做完整 QA 矩阵、多环境巡检或分支部署
- 不更新 `tasks/` 以外的 `docs/`、`memory/` 或 `AGENTS.md`，除非本次 task 的目标就是改这些文件
- 不归档到 `tasks/done/`
- 不 merge 到 `main/master`
- 不 bump 版本号、打 tag、创建 PR
- 不默认 commit 或 push；需要稳定中间点时，后续单独使用当前宿主对应的 `codev-checkpoint` 入口

## Workflow

1. 定位仓库根目录并选择目标任务文件；如果没有待办任务，明确告知并停止。
2. 完整读取任务文件，提取：
   - 目标与背景
   - 验收标准
   - 依赖任务
   - 约束、备注、相关代码入口
   - 已有的 `Implementation Plan` 与 `Validation Plan`
3. 检查当前 git 分支与工作区：
   - 默认直接在当前分支继续，不因 task 文件名创建或切换分支。
   - 如果用户明确要求切到某个分支，且工作区足够安全，则按用户要求切换。
   - 如果存在未提交改动导致无法安全继续，明确报告阻塞并停止。
4. 检查依赖任务是否已完成：
   - 如果前置任务未完成或明显缺前提，不要绕过。
   - 先把阻塞原因写入任务文件，再向用户说明并停止。
5. 初始化或补齐任务文件中的过程记录区：
   - 保留原有目标、范围和验收结构。
   - 保留并持续维护已有的 `Implementation Plan` 与 `Validation Plan`。
   - 如有必要，补充 `## Status`、`## Execution Log`、`## Implementation Notes`、`## Pending Validation`、`## Remaining Gaps` 等小节。
6. 在开始编码前先校准 task plan：
   - 优先完整读取任务文件中已有的 `## Implementation Plan` 与 `## Validation Plan`。
   - 如果代码现状与原计划有轻微漂移，先在任务文件里直接更新这些小节，再开始编码。
   - 如果漂移已经上升到产品范围或架构路径冲突，明确说明并停止；必要时建议用户回到 task 文件继续收敛，或补跑 `plan-eng-review` / `autoplan`。
7. 分阶段实现代码：
   - 优先按容易收敛的小块推进，而不是一次性铺开。
   - 优先复用当前 repo 已有模式，而不是凭空设计新结构。
   - 每完成一个重要里程碑，就更新一次任务文件中的执行记录和实现说明。
   - 若本阶段改了 schema 或迁移，不要把迁移留到全部写完才做；尽早执行仓库约定的迁移，避免后续测试建立在旧库上。
8. 在实现收尾时自动执行一次语义不变精简：
   - 优先沿用 `codev-simplify` 的约束：不改行为、不改公共 API、不引入新依赖、不无故扩大范围。
   - 只在本次 task 相关、已经完成实现的最小必要 diff 上执行这一次；不要在中途重复多轮精简。
   - 如果没有把握，就保持当前实现不改，并在结果里明确说明“没有安全可做的精简”。
9. 精简后按当前仓库约定做完可做验证，顺序固定为迁移、编译、基本端到端：
   - 先读根 `AGENTS.md`、`README.md`、`memory/`、任务文件、启动脚本和 manifest，现场推导命令；不要凭空发明，也不要在本 skill 中写死项目专属路径、端口或服务名。
   - 有 schema、迁移文件或依赖新表的改动时，必须先跑仓库约定的 migrate，并确认数据库/新表可用。未迁移就停下来等用户，属于错误结束。
   - 再跑仓库默认 build / 最小编译校验，优先使用已经稳定存在的单一入口，例如 `pnpm build`、`npm run build`、`cargo build --workspace`、`turbo build`、`just build`、`make build`。
   - 再跑当前环境能做的基本端到端验证：本次改动相邻的单元/集成测试；仓库要求时启动本次代码的 Web 和所需 Worker，等待健康；用仓库约定的 base URL 跑任务专属 E2E，完整 E2E 能跑时一并跑完；涉及已配置外部接口时做脱敏的真实探测或查询。
   - 本地能点通却跑不通的能力，应在本轮删掉页面、后台逻辑和多余表，不要留一个失败壳给用户试。
   - 只有当前环境确实缺少前提的项，才可以留到 `Pending Validation`，例如未配置的生产回调、真实收件人触达、备份恢复演练或多视口人工观感。必须写清缺什么、为什么本地做不到。
   - 不默认触发 `design-review`、完整 QA 巡检、部署或发布。
   - 如果 migrate、build 或可做的端到端验证失败，要修到通过，或明确停在阻塞态；不得假装 task 已可验收。
   - 如果目标仓库约定用户会通过启动脚本做人工验收，不能只把仓库级 build 当作启动预热完成；必须按脚本真实 `cwd + command` 预编译会触发耗时编译的服务或 binary，并把命令与结果写入 task 文件和最终回复。
10. 验证后再次同步任务文件：
   - 实际实现与原计划的差异
   - 已改动的重要文件与模块
   - 精简结果或未精简原因
   - 迁移、默认 build / 最小编译校验、以及已执行的基本端到端验证的命令与结果
   - 尚未执行、且当前环境确实做不到的人工验证
   - 剩余缺口、风险和建议的下一步
   - 当前状态只有在可做验证都通过后，才写成“实现完成，待人工验证”；若验证被跳过或失败，必须写成阻塞或未完成。
11. 用中文向用户汇报：
   - 当前 task
   - 当前分支
   - 已完成的代码实现
   - 本次自动精简的结果
   - 迁移、编译和已执行端到端验证的命令与结果
   - 尚未执行、且本地做不到的人工验证
   - 下一步：用户只验收本地做不到的项；通过后再用当前宿主对应的 `codev-quickship` 入口。Grok 或 Claude Code 写 `/codev-quickship`，Codex 写 `$codev-quickship`

## Rules

- 默认一次只处理一个 task。
- 默认按最小整数任务号选择待办任务，不扫描 `tasks/done/`。
- 任务文件不是只读输入；实际实现路径变化时，必须按事实同步 task。
- 自动精简是 `codev-taskdev` 的内置收尾步骤，不需要在同一轮实现结束后再额外显式调用一次 `codev-simplify`。
- 面向用户提示下一步 `codev-quickship` / `codev-checkpoint` 入口时，必须按当前宿主写调用前缀，不要照抄文档里的 `$` 示例。
- 迁移、默认 build / 最小编译校验和当前环境能做的基本端到端验证，是 `codev-taskdev` 的内置收尾门禁；后续 `codev-quickship` / `codev-checkpoint` 不再补做这些步骤。
- 不要为了“顺手收口”而替用户执行部署、归档或发布。
- 不要把“等用户验证”当成跳过 migrate、build、启动服务或可做 E2E 的理由。
- 不要把 task 收尾同步扩大成 repo 级文档巡检；`docs/`、`memory/`、`AGENTS.md` 的更新留给后续 `codev-quickship`，除非本次 task 的目标就是改这些文件。
- 不要假设必须 commit 才算完成；`codev-taskdev` 默认停在代码、任务文档和可做验证都已完成的阶段。

## Hard Blockers

只有在以下情况才停下来问用户：

- 产品范围或行为出现冲突性决策，且无法从 task、repo 或现有模式中安全收敛
- 依赖任务未完成，继续执行会制造错误前提
- 环境或未提交改动导致无法安全在当前分支继续
- 实现过程中暴露出多条高影响实现路径，无法安全默认选择
- 某项验证缺少当前环境前提，且无法用已有配置安全补齐

如果遇到硬阻塞：

- 先把当前状态和阻塞原因写入任务文件
- 再用中文向用户说明已经完成到哪一步、缺什么、需要用户给出什么最小输入
- 不得把“还没迁移”“还没启动服务”“还没跑能跑的测试”写成需要用户验证的项

## Output

默认返回中文总结，不输出大段源码或完整 patch。

结果中至少包含：

- 任务文件名
- 当前分支
- 当前阶段状态
- 已完成的重要实现
- 本次自动精简的结果
- 迁移、默认 build / 最小编译校验、以及已执行的基本端到端验证的命令与结果
- 尚未执行、且本地做不到的人工验证
- 剩余风险或待验证项
- 下一步推荐的手动动作：用户只验收本地做不到的项，再运行 `codev-quickship`
