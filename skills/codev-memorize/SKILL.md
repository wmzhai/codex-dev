# Memorize

把项目整理成一套任意宿主都能快速上手、快速定位、快速更新的记忆体系。

这个 skill 只做一件事：围绕当前仓库的真实状态，建立或刷新公共 `memory/`，以及三份宿主入口。目标不是写百科，而是让新来的 session 在最短路径内知道先读什么、问题去哪里找、约束从哪里继承、更新该落到哪些文档。无论当前会话是 Codex、Grok 还是 Claude Code，都必须一次写齐全部入口，不能按本机装了哪个客户端裁剪项目文件。

## 第一规则：先用中文交流

- skill 一触发，第一句就用中文和用户交流。
- 整个执行过程中的进度更新、阻塞说明和结果汇报默认都用中文。
- 新增或更新的 `memory/` 文档与三份入口默认都用简体中文。
- 只有用户明确要求英文或双语时，才切换交流语言；除非用户明确要求，否则 repo 内文档仍保持简体中文。

## 调用前缀

面向用户写出下一步 skill 入口时，必须使用当前宿主的调用前缀，不要把另一套宿主的前缀写进用户提示：

- Codex：`$<skill-name>`，例如 `$codev-issue2task`
- Grok / Grok Build TUI：`/<skill-name>`，例如 `/codev-issue2task`
- Claude Code：`/<skill-name>`，例如 `/codev-issue2task`

判断依据：

- 当前会话身份是 Grok 或 Claude Code，或用户是用 `/skill` 触发的，用 `/`
- 当前会话身份是 Codex，或用户是用 `$skill` 触发的，用 `$`

落盘到 `memory/`、`docs/`、`README.md` 的调用说明必须同时列出三家，不能只写当前宿主。

## 核心原则

- 让 `memory/` 只写一份公共事实、约束和落点。
- 让三份入口只回答“我是谁、用什么前缀、去哪里读公共内容”。
- 让每个 memory 文档回答一个明确问题：先去哪里、看哪层、改哪里、验证什么。
- 只写已验证的事实，不写推测。
- 如果是全新项目、代码和目录结构还没长出来，可以把 `README.md` 和用户明确给出的输入信息当作初始事实来源，先搭记忆骨架。
- 所有新增或更新的项目文档默认使用简体中文撰写。
- 旧信息失效时直接删或改，不保留过期路线。
- 谁初始化，另外两家都要能接手：禁止因为当前是 GPT 就只写 `AGENTS.md`，也禁止因为当前是 Claude 就只写 `CLAUDE.md`。

## 目标结构

优先把项目整理成下面这类骨架；具体目录可按项目规模增减，但三份入口必须都在：

```text
AGENTS.md
CLAUDE.md
.grok/rules/memory.md
memory/
├── README.md
├── core/
│   ├── symptom-routing.md
│   ├── system-map.md
│   ├── invariants.md
│   └── workflows.md
├── <domain-a>/
│   ├── README.md
│   └── ...
└── <domain-b>/
    ├── README.md
    └── ...
```

## 工作模式

### 1. 新项目初始化

当仓库还没有这套体系时，按以下顺序建立：

1. 识别仓库根目录。
2. 扫描现有入口文档与结构信号：`README.md`、`AGENTS.md`、`CLAUDE.md`、`.grok/rules/`、`package.json`、`Cargo.toml`、`pyproject.toml`、`docs/`、`src/`、`app/`、`backend/`、`frontend/`、`packages/`、`tools/`。
3. 如果这是全新项目、代码和目录结构仍然稀薄，则把 `README.md` 与用户明确给出的项目信息一起当作初始事实来源，先建立最小记忆骨架。
4. 识别项目的真实分层、主要业务域、调试入口、部署入口、数据入口；如果这些内容尚未落地，就明确写成“当前约定”或“待实现方向”，不要伪装成已存在代码事实。
5. 创建 `memory/README.md` 与 `memory/core/`，把系统图、路由图、默认动作、稳定约束写进去。
6. 按业务域补充 `memory/<domain>/` 文档，每个文档只覆盖一个问题域。
7. 写齐三份宿主入口，每份都含宿主守卫、默认中文、指向 `memory/`、以及该宿主的调用前缀。不要按当前宿主或本机客户端省略任何一份。

### 2. 既有项目刷新

当项目已有记忆体系时，按最新代码状态增量更新：

1. 先读现有三份入口和 `memory/README.md`，再看 `memory/core/` 和相关领域文档。
2. 对照当前代码、目录结构和入口文件，找出新增、移动、废弃或失效的路径。
3. 更新 `memory/` 中的高优先级规则和最短项目事实。
4. 更新 `memory/README.md` 作为导航总表。
5. 更新 `memory/core/` 中的系统图、症状路由、约束和默认工作流。
6. 更新受影响的领域文档，删掉过期分支，补上新落点和新验证路径。
7. 刷新三份入口：补齐缺失的入口；保留已有入口里的宿主专用段落；把与 `memory/` 重复的仓库事实迁走。
8. 如果某个概念已经不再存在，直接移除对应条目，不要留“可能需要”的废话。

### 3. 处理已有入口文件

- 公共事实只保留在 `memory/`。
- `AGENTS.md` 只服务 Codex / GPT；`CLAUDE.md` 只服务 Claude Code；`.grok/rules/memory.md` 只服务 Grok。每份都要写宿主守卫：当前宿主不是自己时，忽略专用前缀规则，只走 `memory/`。
- 如果已有 `CLAUDE.md` 或其它入口含有宿主专用约束，保留这些块，不要删除。
- 不要把 `CLAUDE.md` 写成 `AGENTS.md` 的完整副本或 symlink。
- 不要在入口里继续保留与 `memory/` 重复的长篇仓库事实。
- 落盘文档里的 skill 调用必须同时写 Codex `$name`、Grok `/name`、Claude Code `/name`。

## 记忆文档写法

### 三份宿主入口

每份入口只保留：

- 宿主身份和守卫
- 默认中文
- 公共事实在 `memory/`
- 新会话先读 `memory/README.md` 与 `memory/core/invariants.md`
- 该宿主的调用前缀和本机 skills 路径
- 指向 `docs/workflows.md` 等公共导航

入口必须短。仓库定位、skill 边界、版本规则等公共正文放进 `memory/core/`。

### `memory/README.md`

- 说明 `memory/` 是三家共用的公共正文。
- 列出热路径和冷路径。
- 告诉新会话遇到不同问题时先去哪个子目录。

### `memory/core/symptom-routing.md`

- 按症状到文档的方式写。
- 目标是让新 session 先定位再读源码。
- 一条路由只保留最直接的文件入口。

### `memory/core/system-map.md`

- 只描述仓库的层级边界和数据边界。
- 让新会话知道哪个目录负责什么。

### `memory/core/invariants.md`

- 收录稳定且容易误判的约束。
- 例如数据格式、时间规范、命名边界、禁止做法、默认验证基线。

### `memory/core/workflows.md`

- 记录新会话默认动作和修改后的验证基线。
- 只写高频、可复用、对上手速度有帮助的流程。
- 落盘的下一步 skill 入口同时列出三家前缀。

### 领域文档

- 按项目真实业务域分组。
- 每篇只回答一个明确问题。
- 文档标题要能被快速扫读。
- 每篇都要列出关键入口文件和最可能的修改落点。

## 验证与更新标准

在整理或刷新记忆体系时，优先确认这些信息：

- 项目根目录在哪里。
- 如果是全新项目，`README.md` 和用户输入里已经明确给出的目标、边界和约定是什么。
- 主要执行入口在哪里。
- 共享层和业务层怎么分。
- 调试入口在哪里。
- 部署、恢复、外部联调入口在哪里。
- 哪些规则必须被新会话反复记住。
- 哪些文档已经过期，应该删除或重写。
- 三份宿主入口是否都在，守卫和跳转是否完整。

如果项目后来发生了结构变化，优先让 `memory/` 追上真实状态，再刷新三份入口。

## 输出要求

完成这个 skill 对应的任务时，最终结果应当让下一个 session、换任何一家宿主都能直接做到：

1. 先读对入口文件。
2. 从入口跳进同一份 `memory/`。
3. 快速找到相关代码。
4. 知道该遵守的约束。
5. 知道该更新哪份记忆文档。
6. 所有产出的项目文档默认使用简体中文，避免混入英文默认稿。
